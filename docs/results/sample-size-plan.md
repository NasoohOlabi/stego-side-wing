## Recommended Sample Size

Use successful real samples, not requested samples, as the benchmark size.

| Stage | Successful Samples Per Variant | Purpose |
|---|---:|---|
| Smoke | `5-10` | Verify backend, decode, metrics, and output paths |
| Pilot | `25` | Catch obvious failures and estimate runtime |
| Minimum reportable | `50` | Directional comparison |
| Recommended | `100` | Stronger variant ranking |
| Strong claim | `200+` | More defensible across topics/posts |

Recommended target for this repo now: `100` successful real samples per variant.

Do not count failed samples toward the target. Failed samples must be reported separately.

## Why Current Samples Are Not Enough

Existing results are useful, but not enough for final claims because:

- Some runs used older code or unknown dirty working-tree state.
- Recent runs had infrastructure failures, including LLM endpoint `404` errors.
- Some variants have `0/50` successes in newer runs, which likely reflects backend failure rather than true variant quality.
- Several useful real results have only `25` successful samples per variant.
- KLD/JSD are sensitive to post topic and comment style, so small samples can rank variants incorrectly.

## Version-Control Protocol

Before generating benchmark samples:

1. Decide whether the current modified logic is the logic to evaluate.
2. If yes, commit it or create a dedicated benchmark branch.
3. Record the exact commit hash in every run summary.
4. Record whether the working tree was clean.
5. If the working tree is dirty, label the run as exploratory only.

Required run metadata:

- `git_commit`
- `git_branch`
- `git_status_clean`
- `changed_files`
- `config_hash`
- `prompt_hash`
- `variant_manifest_hash`
- `dataset_manifest_hash`
- `metrics_code_hash`
- `llm_backend`
- `llm_model`
- `run_started_at_utc`

Acceptance rule:

- Final benchmark rows require `git_status_clean = true`.
- Dirty-tree runs can be used for debugging only.

## Dataset Protocol

Use a fixed real-post sample list for all variants.

Rules:

- Select one canonical list of post IDs before the benchmark starts.
- Use the same post IDs for every variant.
- Do not allow post reuse unless explicitly running a small smoke test.
- Keep the sample order stable.
- Store the post ID list in the run directory.
- Store a dataset manifest with file hashes for `datasets/news_angles` and `datasets/news_cleaned` inputs used.

Recommended split:

- `100` fixed posts for main comparison.
- Optional `20` extra posts for post-hoc validation after selecting the best variant.

Do not tune variants on the validation posts.

## Backend Stability Protocol

Before the real benchmark:

1. Verify the LLM backend with one API call.
2. Run a `5` sample smoke test for one variant.
3. Confirm no `404`, timeout, or provider auth failures.
4. Confirm receiver decoding works.
5. Confirm metric reports are written.
6. Only then launch the full run.

Backend failures should be classified separately from variant failures.

Failure classes:

- `infrastructure_failure`: network, ngrok, provider, timeout, auth, HTTP `404/5xx`
- `generation_failure`: model returned unusable output
- `decode_failure`: receiver could not recover payload
- `metric_failure`: KLD/JSD/perplexity could not be computed
- `data_failure`: missing post, missing angles, malformed input

Only `generation_failure` and `decode_failure` should count against variant quality. Infrastructure failures should trigger rerun for the affected sample.

## Benchmark Run Plan

### Phase 1: Freeze Logic

- Finish or revert the currently modified stego/prompt files.
- Run targeted tests for sender/receiver behavior.
- Run full checks if the logic changed materially:
  - `uv run pytest -q`
  - `uv run pyright`
- Commit the benchmark logic.
- Record the commit hash.

### Phase 2: Build Canonical Sample List

- Select `100` real post IDs with usable angles and matching cleaned dataset files.
- Save the list as a benchmark input artifact.
- Generate hashes for all selected input files.
- Reuse the exact same post IDs for every variant.

### Phase 3: Smoke Test

Run `5` samples for one stable variant, preferably `security_legacy` or `sec_v2_anchored`.

Pass criteria:

- At least `5/5` infrastructure success
- Metrics JSON written
- Receiver decode attempted
- No backend `404` or auth errors

If smoke fails, stop and fix infra before collecting benchmark samples.

### Phase 4: Pilot Run

Run `25` samples per variant.

Purpose:

- Estimate runtime
- Identify obviously broken variants
- Confirm failure classification
- Confirm metric ranges are plausible

Do not publish final conclusions from this phase unless clearly labeled as pilot.

### Phase 5: Main Run

Run until each variant reaches `100` successful real samples.

For each variant, track:

- requested samples
- successful samples
- failed samples by class
- rerun count
- average runtime
- matched-post KLD/JSD
- global-corpus KLD/JSD
- receiver success rate
- hidden expansion ratio
- bps total
- unique selection signatures

If a sample fails due infrastructure, rerun the same post ID for the same variant after backend recovery.

### Phase 6: Analysis

Create one final table with these columns:

- variant
- code commit
- clean tree yes/no
- successful samples
- infrastructure failures
- generation failures
- decode failures
- matched-post KLD
- matched-post JSD
- global KLD
- perplexity
- receiver success rate
- hidden expansion ratio
- bps total
- recommendation

Rank variants by goal, not by one metric only:

- Best reliability: highest receiver success, lowest decode failures
- Best stealth: lowest matched-post KLD/JSD
- Best security candidate: secure transform plus good reliability and acceptable KLD/JSD
- Best capacity: highest bps with acceptable stealth/reliability

## Stop Conditions

Stop the benchmark if:

- LLM backend produces repeated `404`, auth, or timeout errors.
- More than `10%` of attempts fail due infrastructure.
- Dataset files change during the run.
- Git working tree becomes dirty during the run.
- Prompt/config files change during the run.

If any stop condition is hit, mark the run as invalid or exploratory.

## Minimum Publishable Result

A result is publishable only if:

- The run used a clean committed code version.
- Every compared variant used the same post ID list.
- Each included variant has at least `50` successful real samples.
- Failures are categorized.
- Infrastructure failures are not confused with variant failures.
- The report includes commit/config/dataset provenance.

Preferred publishable result:

- `100` successful real samples per variant
- clean git tree
- stable backend
- no dataset changes
- final `metrics/INSIGHTS.md` generated from the run summaries
